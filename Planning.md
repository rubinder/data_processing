The repository contains spark applications and various ways to deploy and run data pipelines.
AWS Deployment is under aws_deployment folder, it has a cloudformation template, code for specific to AWS, and deployment code specific to AWS.
Local Spark Deployment is under local_spark_deployment, contains dockerfile to deploy spark cluster locally user and it connects to the airflow cluster mentioned above
Airflow Deployment is under airflow_deployment, it contains a dockerfile to deploy airflow locally using docker, shell scripts to create it, a shell script to deploy dag bundles which contains workflows that contain spark applications. The Spark Applications are run in the AWS environment mentioned above or in the local spark cluster mentioned above
The actual Spark Applications are under spark_applications and are in pyspark. api_pull lands the raw file transactionally (staged, then promoted with a _manifest.json once the table write succeeds) and runs volume and quarantine-ratio checks against the previous days' manifests; aggregation can enrich events with a user dimension using a broadcast-first, salted-on-request join. The spark_applications/debugging package holds seven runnable debugging cases over the same impression data — skewed joins, driver OOM, lost partition pruning, the small-files explosion, AMBIGUOUS_REFERENCE, PythonException from a UDF, and Python UDF to pandas UDF. Each reproduces the pathology, captures the query plan evidence that identifies it, applies a fix and captures the plan again, with resolutions and notes written up in spark_applications/DEBUGGING.md and the rationale in DECISIONS.md #7. Its explain_tools module is reusable plan analysis: it captures the post-AQE final plan that explain() does not show, and parses join strategies, shuffle counts and partitioning schemes, PartitionFilters/PushedFilters, and Python-eval operators.
Databricks Deployment should contain databricks specific databricks infrastructure code and deployment to databricks code
Lineage Deployment is under lineage_deployment, a docker-compose for Marquez (OpenLineage API + UI + PostgreSQL) and LINEAGE.md describing how every layer emits OpenLineage events (Spark listener, Airflow provider, Glue/EMR, dbt-ol, manual Athena emission), all switched on by the single OPENLINEAGE_URL variable.
Under web_server_code should contain web server code using FastAPI that serves file based on parameters
Under web_server_local should contain code to deploy web server locally
Under web_server_aws should contain code to deploy web server to AWS mentioned in the beginning
dbt Deployment is under dbt_deployment, it contains a Dockerfile and docker-compose to deploy PostgreSQL and dbt locally using Docker, a shell script to manage deployment, a data loader script that pulls impression data from the web server API into PostgreSQL, and a dbt project that runs analysis models on the impression data including funnel analysis, page type summary, user engagement, and hourly traffic patterns
Flink Applications are under flink_applications and are in PyFlink (Apache Flink 1.18). Contains a hello world batch job using the Table API and cdc_impressions, a streaming job that reads the Debezium topic (Avro via Schema Registry or JSON), computes tumbling-window counts per page_type with exactly-once checkpointing and event-time watermarks, and writes them to an upsert-kafka topic keyed by (page_type, window).
Flink Deployment is under flink_deployment, it contains a Dockerfile, docker-compose to deploy a Flink JobManager and TaskManager locally using Docker, and a deploy.sh script to manage the cluster lifecycle and submit PyFlink jobs
Debezium CDC Deployment is under debezium_deployment, it contains a docker-compose to deploy Zookeeper, Kafka, PostgreSQL (with wal_level=logical), Debezium Connect (built from a derived image with the Confluent Avro converter), Confluent Schema Registry with BACKWARD compatibility, and Kafka UI locally using Docker. SCHEMA_EVOLUTION.md is the measured walkthrough of a source ALTER TABLE (add/rename/drop) travelling through Debezium, the registry's compatibility gate and Flink's DDL-derived Avro reader schema. A deploy.sh script manages the lifecycle, registers the PostgreSQL source connector, lists topics, and consumes CDC events. The source database has tables for impression events, users, and pull status (matching the project's data theme). Connector config is in connectors/postgres-source.json. A sample_changes.sql file provides DML to generate insert/update/delete CDC events.
DuckDB Deployment is under duckdb_deployment, demonstrating DuckDB as an embedded, application-level OLAP engine. An in-process DuckDB sits behind a small FastAPI service that ingests impression data from the web server API (csv.gz) and serves the four established analyses (funnel, page-type summary, user engagement, hourly traffic) as JSON endpoints. Contains a Dockerfile, docker-compose, deploy.sh, README, uv pyproject, and pytest tests that run real in-process DuckDB queries via FastAPI TestClient.
ClickHouse Deployment is under clickhouse_deployment, demonstrating ClickHouse as a distributed OLAP engine for concurrent queries across multiple nodes. A real multi-node cluster (two shards + clickhouse-keeper) runs a Distributed table over ReplicatedMergeTree. A clickhouse-connect loader ingests impression data from the web server API, and four analytical SQL queries mirror the dbt analyses. Contains docker-compose, cluster/keeper/macros config, init schema, deploy.sh, README, uv pyproject, and pytest tests that execute the analytical SQL against embedded ClickHouse (chdb) plus mocked-request loader tests.
Real-time Analytics is under realtime_analytics, a self-contained Kafka -> PyFlink -> ClickHouse -> FastAPI pipeline over AI agent conversation events (conversation_started, message_sent, agent_response, resolution, escalation) for a multi-tenant conversational-AI platform. It contains a Kafka producer, a simple batching Python consumer, a PyFlink streaming job with documented parallelism/watermark/checkpointing/state-backend/backpressure tuning, a staged set of ClickHouse schemas (naive -> types+codecs -> sorting key -> partitioning -> skipping indexes -> materialized views, plus a projections alternative), a production schema with ReplacingMergeTree and TTL, a FastAPI service serving aggregates from materialized views with a p95 target under 100ms, and benchmark scripts that measure every optimization stage and verify all stages return identical results. The README is self-contained and documents the measured tuning journey, including the negative results.
Iceberg Deployment is under iceberg_deployment, demonstrating the Apache Iceberg table format on Spark 3.5 over the same impression event model. It covers safe schema evolution (field-ID based rename/drop/re-add/widen, with a documented compatibility policy), partition-spec evolution without rewriting data, time travel and rollback via snapshots, MERGE INTO upserts and row-level deletes on format-version 2 merge-on-read tables, and table maintenance (compaction, snapshot expiry, orphan file removal). Contains a filesystem-catalog path that needs no services and a docker-compose Iceberg REST catalog on MinIO for the production shape, plus deploy.sh, a printed six-step demo, README, uv pyproject, and 22 pytest tests that run against real Iceberg tables.
Polars Deployment is under polars_deployment, demonstrating Polars as a single-node, in-process DataFrame engine and the batch counterpart to the DuckDB module. It ingests impression partitions from the web server API straight from gzip CSV bytes into typed frames, stores them as hive-partitioned Parquet (page_type/date/hour, idempotent per-partition replacement), and expresses the four established analyses as lazy LazyFrame pipelines that the optimizer prunes (partition files, columns and unused aggregates) before anything is read. A CLI (load, query, explain, partitions) runs the same plan on the in-memory or streaming engine. benchmarks/bench_engines.py measures eager vs lazy vs streaming vs DuckDB over the same files, each pair in its own subprocess for peak RSS, verifies every engine's answer against the others, and the README records the result: single-node engines finish these analyses on 8M rows in under a second, lazy wins only when the query is narrower than the store, the streaming engine loses on high-cardinality aggregates and wins on filter-and-sink passes. 29 tests hold the analyses to the DuckDB module's fixture numbers on both engines.
Pinecone Deployment is under pinecone_deployment, a similar-conversation retrieval layer over the AI agent conversation events: a deterministic synthetic corpus with labelled intents, pluggable embedders (stdlib hashing, sentence-transformers, Pinecone Inference), a store with deterministic ids, batched idempotent upserts and both tenant-isolation strategies (namespace per account or metadata filter), hybrid sparse-dense search with hashed BM25, rerankers, an evaluation harness (recall against exact kNN, intent precision, latency, freshness), an embedding-model migration flow (shadow index, dual write, cutover pointer) and a FastAPI service. Tests and benchmarks run against Pinecone Local in Docker; hosted models and serverless measurements need an API key.
Ops Agent is under ops_agent, a contracts-driven, rules-first operations agent over the Iceberg impression tables that iceberg_deployment creates (ported from the standalone autonomous_data_platform project and pointed at this repository's event model). feeds/impressions.yaml declares the feed's layers, contracts, monitors and arrival SLA; contracts/*.yaml declare each table's schema, fail-closed expectations and enum watches in Iceberg's type vocabulary. A Spark engine reads schema history with field IDs and per-snapshot row counts from table metadata, so the sensor never scans the lake for what metadata already knows. A LangGraph graph runs sense -> monitor -> classify -> persist -> act: schema drift is classified breaking / renaming / widening / additive with renames paired by field ID (one rename is one finding, not a phantom drop plus a phantom add), enum drift is recorded and never blocks, volume is judged per snapshot on the append-only table and by count(*) on the rebuilt one, and monitor baselines are persisted in ops.monitor_results with median/MAD verdicts. Actionable findings write stable-slug incident files and, only with --execute, GitHub issues. The daily report reads ops.* and diffs findings day over day; it never recomputes. The aggregated table is contract-gated before it is published. An LLM is consulted only for findings no rule matches, never in tests.

MCP Deployment is under mcp_deployment, the governed agent-access layer over the gold datamart that dbt_deployment builds on PostgreSQL (now the pgvector image). sql/ applies least-privilege roles per pipeline stage (ingestion, transform, promotion, mcp_reader), a blue-green promotion into a gold schema done by one SECURITY DEFINER function that copies the dbt analysis models into a versioned release schema, grants the reader, swaps schema names in one transaction and logs the release, with a rollback function and three-release retention, and a pgvector catalog. catalog.py generates one entry per gold table, column and query template from the dbt manifest and catalog artifacts and syncs by content hash. templates/*.yaml are the only queries the agent can run: typed parameters with choices and ranges bound server-side, a row cap, a statement timeout, and a load-time lint that rejects anything that is not a single SELECT over gold. server.py is a FastMCP server with five read-only tools (search catalog, list/describe templates, describe table, run template) connecting as mcp_reader, which can SELECT gold and the catalog and nothing else; there is no tool that takes SQL. Embeddings default to a dependency-free hashing embedder with sentence-transformers optional.
