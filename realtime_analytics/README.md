# Real-time analytics for AI agent conversations

**Kafka → PyFlink → ClickHouse → FastAPI**, with the ClickHouse tuning work
measured stage by stage rather than asserted.

A conversational-AI platform runs AI agents for many brands across chat, voice,
email, SMS, and API. Every interaction emits events. Two groups of people need
to query those events within milliseconds: the customers, who watch resolution
and escalation rates for their own tenant, and the on-call engineer, who
watches agent latency across the whole fleet.

This module builds that pipeline and then optimizes the storage layer, one
variable at a time, recording what each change actually bought.

**Headline: the tenant dashboard query went from 181 ms to 2.4 ms (75×) and the
platform-wide query from 286 ms to 2.0 ms (143×), reading 91 rows instead of
12,000,000. On the deployed stack the API answers every endpoint at a p95 of
8.5 ms against a 100 ms target (1.2 ms in-process, without the network hop).**

Every number here comes from a script in `benchmarks/`, is reproducible on a
laptop with no server running, and is checked for correctness before it is
reported — a stage that returns different numbers faster is recorded as a
failure, not a speedup.

> **[OPTIMIZATIONS.md](OPTIMIZATIONS.md) — the companion explainer.** This
> README is the *results* reference. That document is the *reasoning*: how
> ClickHouse actually reads data (granules, marks, parts), why each
> optimization follows from that mechanism, where each one stops helping, and
> a decision procedure for choosing between them on a different schema.

![ClickHouse tuning results: tenant dashboard 181.1 ms to 2.4 ms, platform-wide

| Query | Naive | Tuned | Speedup | Rows read: before → after |
| --- | ---: | ---: | ---: | --- |
| Tenant dashboard (1 account, 7 days) | 181.1 ms | **2.4 ms** | **75×** | 12,000,000 → 128 |
| Platform-wide health (all tenants, 7 days) | 285.7 ms | **2.0 ms** | **143×** | 12,000,000 → 91 |
| Slow-response triage (latency > 5 s) | 204.3 ms | **4.8 ms** | **42×** | 12,000,000 → 90,112 |
| Conversation drill-down (single UUID) | 26.0 ms | **3.7 ms** | **7×** | 12,000,000 → 186,479 |

## The data model

The domain is deliberately concrete. An end customer talks to an AI agent and
the conversation either resolves or escalates to a human.

| `event_type` | Meaning |
| --- | --- |
| `conversation_started` | a customer opened a conversation |
| `message_sent` | the customer sent a message or utterance |
| `agent_response` | the AI agent replied — carries model, latency, tokens |
| `resolution` | the agent closed the conversation successfully |
| `escalation` | handed off to a human, with a reason |

Every event carries `account_id` (the brand — this is a multi-tenant platform),
`conversation_id`, `channel` (`chat`/`voice`/`email`/`sms`/`api`), `model`,
`intent`, `event_ts`, and `ingest_ts`.

Three properties of the generated data exist specifically to make the tuning
work meaningful, and they are what a synthetic dataset usually gets wrong:

- **Tenant traffic is heavily skewed.** The largest account holds roughly a
  third of all events. Benchmarks run against *that* tenant, because it is the
  one whose dashboard is slow; tuning against the median tenant hides the
  problem you were hired to fix.
- **Agent latency has a long tail.** ~92% of responses are fast, ~7% slow, ~1%
  pathological. Without a tail, p95 and p99 are indistinguishable from the mean
  and every percentile decision becomes arbitrary.
- **`ingest_ts` lags `event_ts` by 20 ms – 2.5 s**, and the producer can inject
  events minutes late. That lag distribution is what the Flink watermark is
  tuned against.

`realtime_analytics/events.py` generates these in Python for the streaming path.
`realtime_analytics/data_gen.py` generates the *same logical data* as an
`INSERT … SELECT FROM numbers()` for the benchmark, because 12 million rows
through a Python producer would measure the producer, not the database. Both are
deterministic, so every table in the benchmark holds byte-identical data and no
stage can win by accident.

## Why ClickHouse and not Redshift

The workload has a specific shape, and it is the shape ClickHouse is built for.

**The queries are narrow and the tables are wide.** The tenant dashboard touches
4 of 18 columns. A columnar engine reads only those; ClickHouse read 1.3 MB to
answer a query over a 405 MB table. Redshift is also columnar and would do this
well — this is not the differentiator.

**The access pattern is "one tenant, one recent time range," at interactive
latency, continuously.** ClickHouse's sparse primary index over the physical
sort order turns that into a mark-range scan: measured, it dropped the query
from reading 12,000,000 rows to 90,112. Redshift's equivalent — sort keys plus
zone maps — is real but coarser, and its per-query overhead is tens to hundreds
of milliseconds before any data is touched. When the target is a 2 ms p95, fixed
overhead in that range is the whole budget.

**Incremental materialized views are the deciding feature.** ClickHouse
maintains a pre-aggregate on insert, transactionally with the write, and merges
partial aggregate states — including quantile sketches — on read. That is what
took the platform query to 2.0 ms and 91 rows. Redshift materialized views
refresh on a schedule or on demand, so you choose between staleness and a
periodic expensive rebuild. AggregatingMergeTree has no refresh: it is always
current because it is part of the write path.

**Ingest is a continuous stream, not a batch load.** ClickHouse ingests directly
from Kafka or a JDBC sink at high rates with no staging layer. Redshift is
happiest with batched `COPY` from S3, which adds a staging hop and minutes of
latency to a pipeline whose point is freshness.

**Cost model.** Redshift bills for a provisioned cluster sized for peak;
ClickHouse runs on ordinary compute you already operate, and the compression
measured here (3.0× on the tuned schema, 405 MB for 12 M events) keeps the
footprint small.

**Deployment topology.** This is decisive for customer-managed and on-prem
installations: ClickHouse is a binary you can run anywhere, including
air-gapped. Redshift exists only inside AWS. Any analytics feature built on
Redshift cannot ship into a customer's own VPC or data centre.

**When Redshift or BigQuery would be the better answer**, honestly: if the
workload were overnight batch reporting rather than interactive dashboards; if
it needed heavy multi-table joins across a normalized warehouse (ClickHouse's
join planner is far behind, and this schema is deliberately wide and
denormalized to avoid them); if the team already lived in an AWS analytics
estate and operational simplicity outweighed latency; or if strict transactional
correctness with immediate `UPDATE`/`DELETE` semantics were required, which
ClickHouse's merge-time deduplication does not provide.

## The tuning journey

The stage-by-stage results are below. For *why* each change works —
the storage mechanism it exploits, and the cases where it does nothing — see
**[OPTIMIZATIONS.md](OPTIMIZATIONS.md)**.

### How it was measured

The method matters more than the numbers, because a benchmark is very easy to
accidentally rig.

- **One variable per stage.** Stage *N* differs from stage *N−1* by exactly one
  schema decision. The data is generated once and copied into each table, so a
  stage cannot win by holding different rows.
- **Results are verified, not assumed.** Every stage's output is compared
  against the naive baseline before any speedup is reported. Counts must match
  exactly; percentiles must agree within 5%, because t-digest sketches merged
  from many partial states are not bit-identical to a single-pass computation.
  The observed drift was 0. Any mismatch shows as `correct: NO`.
- **Even the naive query uses `quantileTDigest`.** Had the baseline used a
  heavier aggregate, part of the "speedup" would have been the function change
  rather than the schema work.
- **Interleaved rounds, not one table at a time.** Every table is warmed, then
  all stages are measured round-robin. This was not a stylistic choice: the
  first version of the harness measured each table to completion and reported a
  2.6× *regression* for partitioning that vanished entirely once the order was
  interleaved. It was cache warmth, not schema.
- **The ClickHouse query condition cache is disabled** (`use_query_condition_cache=0`).
  It is on by default in ClickHouse 25+ and caches which granules matched a
  predicate, so re-running a query makes an *unindexed* table behave like an
  indexed one. It was silently erasing most of the measured value of the bloom
  filter. The serving API leaves it enabled, because there it is a real win.
- **The engine's own accounting is reported** alongside wall clock. `rows_read`
  and `bytes_read` explain *why* something got faster; wall time alone does not.

**The engine's own index analysis is committed too**, in
[`benchmarks/results/explain.md`](benchmarks/results/explain.md). It is the
shortest path to seeing *why* each stage is faster — `EXPLAIN indexes = 1`
reporting how many granules survive pruning:

| query | no index | + sorting key | + partitioning | + bloom filter |
| --- | ---: | ---: | ---: | ---: |
| tenant dashboard | 246/246 | **2**/245 | 2/247 | 2/247 |
| platform-wide | 246/246 | 201/245 | **73**/247 | 72/247 |
| conversation drill-down | 246/246 | 245/245 | 247/247 | **4**/247 |

Each row shows the same query against schemas differing by one decision. A
granule is 8192 rows and unselected granules are never read, so those ratios
*are* the speedups — and each optimization is decisive for exactly one query
and irrelevant to the others, which is the whole argument for choosing them per
access pattern rather than applying all of them everywhere.

Environment: Apple M3, 8 cores, 16 GB, ClickHouse 26.5 embedded in-process via
[`chdb`](https://github.com/chdb-io/chdb) — the real engine, same SQL, no
server. Absolute numbers on server hardware will differ; the ratios and the
`rows_read` figures are the transferable part. `--backend http` runs the
identical benchmark against a real cluster.

### Stage 0 — the naive baseline

`clickhouse/00_naive.sql`. Not a strawman — it is what you get when a table
mirrors the wire format: every column `String` including timestamps, the numeric
measures buried in a JSON blob, `ORDER BY tuple()`, no partitioning.

```sql
ENGINE = MergeTree
ORDER BY tuple()          -- no primary index: every query is a full scan
```

**181 ms** for the tenant dashboard, reading all 12,000,000 rows and 2.0 GB.
It works. At small volume nobody notices. It falls over exactly when the dataset
outgrows the page cache.

### Stage 1 — physical types and codecs

`clickhouse/01_types_codecs.sql`. **181 ms → 49 ms (3.7×)**, still reading every
row.

The sorting key is deliberately left as `tuple()` so this stage isolates one
question: how much of the naive cost was reading and parsing badly typed data?
Answer: three quarters of it.

| Change | Why |
| --- | --- |
| `DateTime64(3)` instead of ISO text | removes `parseDateTimeBestEffort` from the hot path — the single most expensive operation in the naive query |
| `CODEC(Delta, ZSTD)` on timestamps | event streams are near-monotonic, so consecutive deltas are tiny |
| `CODEC(T64, ZSTD)` on numerics | latency and token counts never approach `UInt32`'s range; T64 transposes the bit planes and the zero high bytes vanish |
| `LowCardinality(String)` on dimensions | a dictionary index instead of a string, shrinking both storage and `GROUP BY` key comparison |
| `UUID` instead of `String` for ids | 16 fixed bytes instead of 36 text bytes plus a length |
| JSON blob unpacked into real columns | a query needing latency reads the latency column, not every measure |

Bytes read fell from 2012 MB to 168 MB — a 12× reduction — for a 3.7× latency
win. The gap is CPU: the engine still decompresses and evaluates 12 M rows.

### Stage 2 — the sorting key

`clickhouse/02_sorting_key.sql`. **49 ms → 7.1 ms (25× cumulative)**, and rows
read collapse from 12,000,000 to **90,112**.

```sql
ORDER BY (account_id, event_ts)
```

This is the single highest-leverage decision in a ClickHouse schema. The sorting
key *is* the physical row order, and the primary index is a sparse mark every
8192 rows, so a filter on a key prefix becomes a mark-range scan and everything
else is skipped without being read.

Why this order:

- **`account_id` leads** because essentially every customer-facing query is
  scoped to one tenant. It also keeps a tenant's rows physically contiguous,
  which makes per-tenant reads, deletes, and GDPR erasure cheap.
- **`event_ts` is second** because within a tenant every dashboard asks for a
  time window, and sorted-by-time inside a tenant makes a 7-day window one
  contiguous mark range.
- **`event_type` is deliberately absent.** It is tempting — five values, very
  low cardinality — but placing it before `event_ts` would shatter each tenant's
  time ordering into five interleaved runs, so a time-window query without an
  `event_type` filter would scan five disjoint ranges instead of one.

The familiar "order by ascending cardinality" rule is a tiebreaker, not the
primary rule. The primary rule is **match the filter prefix of the query you
must make fast**.

### Stage 3 — partitioning

`clickhouse/03_partitioning.sql`. This stage is where measurement overruled my
first instinct, so it is worth reading even though the headline change is small.

Partitioning helps the query with **no tenant filter** — the on-call fleet-wide
view — where the leading sorting-key column buys nothing:

| | rows read | p95 |
| --- | ---: | ---: |
| unpartitioned | 4,135,376 | 21.3 ms |
| monthly partitions | 2,469,328 | **15.6 ms** |

I originally chose **weekly** partitions, reasoning that a 7-day dashboard
window should map onto one partition. That reasoning counted the pruning benefit
and ignored the cost, and it was wrong.

Every surviving part is work: its index is consulted and its granules are read
separately. `benchmarks/bench_partitioning.py` builds the same 20 M rows four
ways and measures the *same* tenant query over the *same* 147 k rows:

| Partition key | Parts | p50 | vs unpartitioned |
| --- | ---: | ---: | ---: |
| none | 1 | 7.3 ms | — |
| monthly | 3 | 10.6 ms | 1.5× slower |
| weekly | 14 | 19.6 ms | 2.7× slower |
| daily | 91 | **79.8 ms** | **11× slower** |

Roughly **0.8 ms of fixed cost per part**. On the cross-tenant query, finer
partitioning did cut rows read (4.7 M → 1.6 M from none to weekly) but per-part
overhead ate the entire gain — wall time stayed flat at ~25 ms and then went 3.5×
worse at daily.

So the shipped schema partitions **monthly**: coarse enough that the part count
stays in single digits at 90-day retention, fine enough that expiry is a
`DROP PARTITION`. The sorting key does the pruning.

What generalizes is the method, not the number. At billions of events per day a
daily partition is enormous and per-part overhead is negligible against the work
inside it, so daily becomes correct. The rule is to measure **both sides** —
pruning benefit *and* per-part cost — rather than reaching for daily by reflex.

`PARTITION BY account_id` was rejected outright: thousands of tenants means
thousands of tiny partitions and destroyed merge efficiency. Tenant isolation
belongs in the sorting key.

The operational payoff is larger than the query payoff. Retention becomes
`ALTER TABLE … DROP PARTITION` — a metadata operation, instant, no merge
pressure — instead of a `DELETE` mutation that rewrites every affected part.

### Stage 4 — skipping indexes

`clickhouse/04_skipping_indexes.sql`. The support console has the opposite
access pattern: *pull up this one conversation*, filtering on a UUID with
millions of distinct values. The sorting key cannot help, and putting
`conversation_id` in it would destroy the tenant/time ordering everything else
depends on.

```sql
INDEX idx_conversation conversation_id TYPE bloom_filter(0.01) GRANULARITY 1
```

**Conversation drill-down: 10.8 ms → 3.7 ms, rows read 12,000,000 → 186,479.**
A conversation's events are written together in time, so its rows land in a few
adjacent granules and the bloom filter rejects everything else. `GRANULARITY 1`
gives one filter per granule — the most selective setting, which is what a
needle lookup wants. A 1% false-positive rate is the right trade: a false
positive costs one wasted granule read, while a smaller rate costs memory on
every part.

Note what the *unindexed* stages show: 12,000,000 rows read. That is the honest
comparison, and it is only visible with the query condition cache disabled.

### Stage 5 — materialized views

`clickhouse/05_materialized_views.sql`. Stages 1–4 make the scan cheaper. This
one removes the scan. **Tenant dashboard 5.4 ms → 2.4 ms; platform-wide 14.9 ms
→ 2.0 ms, reading 91 rows.**

A ClickHouse materialized view is an **insert trigger, not a cached query**: as
each block lands, the view's `SELECT` runs over that block alone and the result
is written to a target table. The cost is paid once in the streaming path
instead of on every dashboard load.

Two column styles in the `AggregatingMergeTree` target:

- `SimpleAggregateFunction(sum, UInt64)` for counts — sums are associative, so
  the column stores a plain number and merges add them.
- `AggregateFunction(quantilesTDigest(…), UInt32)` for latency — quantiles are
  *not* associative (you cannot average two p95s), so the t-digest sketch itself
  is stored and merged with `quantilesTDigestMerge` at read time. t-digest is
  approximate but most accurate in the tails, which is where p95/p99 live.

Two discoveries here, both of which changed the design:

**The view was initially slower than the scan it replaced.** The aggregate table
holds ~18,000 rows, but `index_granularity` defaulted to 8192 — tuned for tables
with hundreds of millions of rows. One granule was a third of the table, and
every row in it carries a fat t-digest column, so answering a 7-row question
pulled ~5,800 rows and ~1 MB off disk. Setting `index_granularity = 128` made
granule reads precise and took the query from 8.7 ms to 2.4 ms.

**One view cannot serve both audiences.** Answering the fleet-wide query from
the tenant-keyed view means merging one sketch per (account, day) — 200 accounts
× 7 days = 1,400 sketches — and sketch merging is expensive enough that it was
*slower than scanning 1.5 M raw rows*. The fix was not a better index but a
second view keyed on `day` alone (`platform_daily`), making the same answer 7
rows and 7 merges. The general rule: **a view accelerates the grouping it was
keyed for, and a query that groups more coarsely still pays for the view's finer
granularity.**

Three views ship, matching the three dashboards that actually load:
`conversation_daily` (tenant overview), `agent_hourly` (latency SLO tracking by
model and channel), `platform_daily` (fleet-wide).

Caveats that matter in production, all covered in the schema comments:

- A view fires only on rows inserted *after* it is created; existing data must
  be backfilled explicitly. `bench_clickhouse.py` derives the backfill from the
  view's own `SELECT` so the two cannot drift — a very common source of "the
  dashboard disagrees with the raw table."
- A view does not see mutations. `ALTER TABLE … DELETE` on the source leaves the
  aggregate untouched; corrections need a partition rebuild.
- On a sharded cluster the view must be attached to the **local** table on every
  node, never the `Distributed` table, or rows are aggregated twice.

### Stage 6 — projections, the alternative

`clickhouse/06_projections.sql`. A projection is a second physical copy of the
data inside the same table, with its own sort order or pre-aggregation, selected
automatically by the planner.

**For the needle query it is the outright winner: 2.0 ms, reading 24,576 rows —
better than the bloom filter's 3.7 ms and 186,479 rows**, because a re-sorted
copy locates the conversation exactly rather than probabilistically.

But the aggregate projection was **never selected**, and `EXPLAIN` says why: the
query filters on `event_ts`, which the projection does not materialize, so the
planner cannot apply the predicate. A projection only helps queries matching its
shape — precisely the brittleness that argues for materialized views when query
shapes vary.

The deciding factor for this design is lifecycle. Raw events expire at 90 days
while aggregates are kept for two years, and **a projection cannot outlive its
parent part**, so it cannot have a longer retention than the raw data. A
materialized view's target is a real table with its own partitioning, TTL, and
rebuild story. Hence: materialized views ship, projections stay documented as
the alternative — with the honest note that for the drill-down specifically, a
projection is measurably better than the index that shipped.

## What did not work

The failures were more instructive than the wins, and leaving them out would
make the writeup useless to anyone doing this themselves.

**The minmax index on `latency_ms` pruned nothing.** Compare `v3` and `v4` in
the slow-response table: identical rows read (90,112), identical latency. Agent
latency's slow tail is spread uniformly across granules, so with ~8192 rows per
granule essentially every granule contains a row above any interesting
threshold, and the recorded maximum never excludes anything. **Skipping indexes
only pay when the indexed column correlates with physical row order.** Uncorrelated,
they are pure write-side cost — built on every insert and every merge for zero
read benefit. It is removed from the shipped schema (`10_production.sql`), and
kept in stage 4 precisely so the benchmark keeps demonstrating that it does
nothing.

**The aggregate projection was never selected.** It groups by `(account_id, day)`
but the query filters on `event_ts`, which the projection does not carry, so the
planner cannot push the predicate into it. Not a bug — a demonstration that
projections bind to query *shape*.

**The first materialized view was slower than the scan it replaced**, twice
over: once from the default `index_granularity` on a small, wide aggregate
table, and once from asking a tenant-keyed view to answer a fleet-wide question.
Both are described above. A materialized view is not automatically fast; it is
fast when its key matches the query and its granularity matches its size.

**Weekly partitioning was a regression I shipped before measuring it.** See
stage 3. The dedicated experiment is in `benchmarks/bench_partitioning.py`.

**Two measurement bugs nearly published wrong numbers**, which is the part I
would most want a reviewer to check:

1. *Sequential measurement.* Measuring each table to completion made cache
   warmth accumulate against later stages and produced a phantom 2.6×
   regression for partitioning. Fixed by interleaving rounds.
2. *The query condition cache.* On by default in ClickHouse 25+, it caches
   granule-match results per predicate, so the second run of a query against an
   **unindexed** table skips granules exactly like an indexed one. It made the
   bloom filter look nearly worthless (a 3× difference in rows read instead of
   the true 64×). Found because a test asserting the index prunes passed alone
   and failed in the suite — an order-dependent test failure worth chasing
   rather than retrying.

**Four bugs that only a real deployment could find.** Everything above was
found by benchmarks and unit tests against embedded ClickHouse. These needed
actual containers:

1. *ClickHouse rejected every network client.* The official image logs
   "neither CLICKHOUSE_USER nor CLICKHOUSE_PASSWORD is set, disabling network
   access for user 'default'" and then accepts the in-container client over
   localhost while failing every HTTP client. Embedded testing cannot see this
   because there is no network.
2. *The Flink JDBC sink could not exist at all* — no ClickHouse dialect in any
   released connector. See the Flink section; the fix changed the
   architecture, not a parameter.
3. *`scan.startup.mode = 'group-offsets'` with no reset policy* kills the job
   on a brand-new consumer group with `NoOffsetForPartitionException`. It
   fails **only** on the first deploy into a fresh environment — every restart
   during development finds committed offsets and works — which is the worst
   possible failure schedule.
4. *A named volume mounted over a path absent from the image is root-owned*,
   so the `flink` user could not create checkpoint directories. The symptom
   ("Failed to create directory for shared state") points at storage, not at
   ownership.

Two more were environmental but worth recording: PyFlink 1.18 supports Python
≤3.10 while the `flink:1.18.1` base image is now Debian bookworm (3.11 only),
and PyFlink publishes no `aarch64` wheel — so on Apple Silicon the image needs
a standalone 3.10 and `platform: linux/amd64`.

**A tie-ordering bug in the query itself.** `ORDER BY slow_responses DESC` with
tied counts returns rows in scan-dependent order, so the stages disagreed on row
*order* while agreeing on every value. The equality check caught it. The fix is
a deterministic tiebreaker (`ORDER BY … DESC, model, channel`) — which is also a
real API bug fix, since unstable ordering under ties breaks pagination.

The tuned schema stores the same events in **2.5× less space** than the naive

rather than an obvious one.

The three aggregate tables together are ~40 MB against 405 MB of raw events —
about 10%, for the queries that serve nearly all dashboard traffic. Combined
with a 90-day TTL on raw events and 730 days on aggregates, the long-term
footprint is dominated by aggregates that are two orders of magnitude smaller
than the events they summarize.

The design rules that make the target reachable:

- **Dashboard endpoints read materialized views, never raw events.** The raw
  table is reserved for the drill-down and `intents`, where the result set is
  inherently small or the sorting key prunes hard.
- **Every window is bounded.** An uncapped range parameter is how a fast
  analytics API becomes a slow one; `days=100000` is rejected at the edge.
- **All user input is a bound `{name:Type}` parameter**, never formatted into
  SQL, plus shape validation on path parameters. There are tests for the obvious
  injection attempt.
- **The service reports its own latency.** Every response carries
  `X-Response-Time-Ms`, and `/metrics` exposes per-endpoint percentiles in
  Prometheus format. A service that claims a p95 target should be able to answer
  for it without an external load generator. (In a real deployment, export a
  histogram and let Prometheus aggregate across replicas — percentiles cannot be
  averaged after the fact.)

## Flink tuning

`realtime_analytics/flink_job.py` and `flink_sql.py`.

**Flink does exactly one job here: the event-time windowed rollup.** Raw events
are not routed through it — ClickHouse ingests them straight off the same topic
with its Kafka table engine, or the plain Python consumer does. Passing raw rows
through Flink would add a hop, a failure mode, and a duplicate-delivery problem
while buying nothing. Flink earns its place on the one thing ClickHouse cannot
express: watermarks and late-event semantics.

### The JDBC sink that could not exist

The first design sank straight into ClickHouse over JDBC, with the ClickHouse
JDBC driver on the classpath. It fails at submit time:

```
Could not find any jdbc dialect factory that can handle url
'jdbc:clickhouse://analytics-clickhouse:8123/default'
that implements JdbcDialectFactory in the classpath
```

Flink needs a *dialect*, not just a driver, and `flink-connector-jdbc` ships
none for ClickHouse — verified by inspecting the `JdbcDialectFactory` service
files in 3.1.2-1.18, 3.2.0-1.18, 3.3.0-1.20 and 3.4.0-1.20, none of which list
one. The choices are to write and build a custom `JdbcDialectFactory` in Java,
or to hand rows to ClickHouse over Kafka.

The second is both simpler and better, and it is the standard ClickHouse
streaming pattern (`clickhouse/21_flink_rollup_ingest.sql`):

```
Flink window  →  Kafka topic  →  ClickHouse Kafka engine  →  MV  →  MergeTree
```

* ClickHouse batches on its own terms via `kafka_max_block_size`, so the
  one-part-per-flush hazard that makes naive streaming sinks dangerous is gone;
* offsets are committed only after the destination block is written;
* back-pressure shows up as consumer lag — already the thing being alerted on.

The same engine can ingest the raw topic too (`20_kafka_ingest.sql`), as an
alternative to the Python consumer. Run one or the other, never both: two
consumer groups on one topic means every event is inserted twice.

### Verified on the running cluster

Submitted to the compose cluster, against a live producer:

| | |
| --- | --- |
| Windows emitted → ingested | **1,321 → 1,321** (no loss) |
| Distinct 1-minute windows | 23, **all minute-aligned** |
| Events aggregated | 129,862 across 25 tenants |
| Counter consistency | `conversation_started`=12,987 == conversations; `resolution`=10,631 == resolutions; `escalation`=2,308 == escalations |
| Terminal vs started | 12,939 vs 12,987 → 48 conversations still in flight, as expected |

Every knob is a field on `FlinkTuning` with an environment override, so a job can
be retuned without a rebuild, and the config map is asserted on in tests.

### Parallelism

The useful ceiling for a Kafka-sourced job is **the partition count**. Subtasks
beyond that sit idle holding slots — and worse, an idle subtask emits no
watermark, so the global watermark (the minimum across subtasks) stalls and
windows never fire. That failure presents as "the pipeline is healthy but the
dashboard stopped updating," which is why `table.exec.source.idle-timeout` is
set to 60 s to exclude quiet sources from the watermark calculation. The topic is
created with 12 partitions so parallelism can be raised to 12 without
repartitioning.

**Scale up when a subtask is CPU-bound** (busy ratio near 1.0), **not when lag is
high.** Lag caused by a slow sink gets *worse* with more parallelism, because
more subtasks contend for the same sink. Sink parallelism is pinned lower than
job parallelism (2 vs 4) for exactly this reason: *N* sink subtasks produce *N*
times the parts per flush interval, and part count is what kills ClickHouse.

### Watermarks and late events

```sql
WATERMARK FOR event_ts AS event_ts - INTERVAL '30' SECOND
```

This declares: *once I have seen an event at time T, nothing older than T−30 s is
still coming*. Windows fire on that assertion, so the value trades latency
against completeness directly:

- **Too small** → windows close before stragglers land, late events are dropped,
  and the escalation rate reads low. Nobody notices, because the number is
  plausible. This is the dangerous direction.
- **Too large** → every windowed result is delayed by that much, and window state
  is held that much longer.

The value should come from the measured lag distribution — roughly the p99 of
`ingest_ts - event_ts` — not from taste. The producer injects lateness of up to
600 s deliberately (`--late-fraction`) so the choice can be validated rather than
assumed. Flink's `numLateRecordsDropped` metric is the one to alert on; a
non-zero rate means the watermark is too aggressive.

### Checkpointing

| Setting | Value | Reasoning |
| --- | --- | --- |
| interval | 30 s | bounds replay after failure to ~30 s of events |
| **min pause between checkpoints** | 10 s | the setting that most often turns a struggling job into a stuck one — without it, a job taking 25 s to checkpoint on a 30 s interval spends nearly all its time checkpointing and never drains its backlog |
| timeout | 120 s | |
| max concurrent | 1 | concurrent checkpoints hide the fact that checkpointing is not keeping up |
| tolerable failures | 3 | ride out a transient storage blip instead of failing the job and replaying |
| retain on cancellation | yes | resume deliberately rather than from the topic's retention horizon |

Mode is `EXACTLY_ONCE` for state, but note the end-to-end guarantee is **at-least-once**:
Flink's JDBC sink has no transactional coordination with ClickHouse, so recovery
replays the tail of the stream. That is why the target table is a
`ReplacingMergeTree` keyed to collapse duplicates — the storage layer completes
the contract the sink cannot.

### State backend: RocksDB vs heap

- **`hashmap`** keeps state on the JVM heap. Fastest possible access, no
  serialization on the hot path. Correct when state fits comfortably in memory —
  this job's 1-minute windows over a few thousand keys are a few hundred MB at
  most. The failure mode is a GC death spiral, then OOM.
- **`rocksdb`** spills to local disk, so it scales past memory, and it is the
  only backend supporting **incremental checkpoints**, which matters enormously
  once state reaches tens of GB. It costs serialization on every state access —
  expect single-digit-multiple lower throughput on state-heavy operators.

The default here is `rocksdb`, chosen for the production shape of this job
(per-conversation session state with a multi-hour timeout, where state size is
unbounded by anything the job controls). **For the windowed rollup alone,
`hashmap` is the faster and correct choice** — set `FLINK_STATE_BACKEND=hashmap`.
The honest rule: heap until state outgrows memory or checkpoint duration
outgrows the interval, then RocksDB.

### Backpressure

Diagnosis, in order: the Flink UI's backpressure view identifies *which* operator
is the bottleneck (the busy one immediately downstream of the backpressured
one); `numRecordsOutPerSecond` per subtask shows whether it is skew (one hot
subtask) or global; checkpoint duration climbing in step with backpressure
confirms barriers are stuck behind buffered data.

Three remedies, all configured here:

1. **Unaligned checkpoints** (`FLINK_UNALIGNED_CHECKPOINTS=true`) — the direct
   fix for backpressure stalling checkpoints. Barriers overtake in-flight data
   rather than queueing behind it, at the cost of storing those buffers in the
   checkpoint. Enable when checkpoint duration tracks backpressure; leave off
   for a job that is never backpressured, since it inflates checkpoint size.
2. **Two-phase (local-global) aggregation** (`table.optimizer.agg-phase-strategy=TWO_PHASE`)
   — the standard answer to a hot key. With one tenant holding a third of all
   traffic, the single-phase plan routes every one of its records to one
   subtask; two-phase pre-aggregates locally before the shuffle.
3. **Mini-batch aggregation** — buffers records and does one state access per key
   per batch instead of per record. On a keyed aggregation this is typically the
   largest single throughput win available, and it costs exactly
   `mini_batch_latency_ms` (1 s) of added latency.

If the bottleneck is the sink rather than the operator graph — the common case
here — none of those help, and the fix is sink-side: larger
`sink.buffer-flush.max-rows`, or fewer sink subtasks.

## Three ways to ingest, and when each is right

There are three paths into ClickHouse here, and keeping all three makes the
trade-off concrete instead of theoretical. **Flink is not one of them** — it
does the event-time rollup, not raw ingest.

| | Python consumer | ClickHouse Kafka engine | Flink |
| --- | --- | --- | --- |
| Role | raw ingest | raw ingest | **windowed rollup only** |
| Runs where | one extra process | inside the database | JobManager + TaskManagers |
| Batching control | `--batch-size` / flush timer | `kafka_max_block_size` | n/a |
| Delivery | at-least-once (commit after insert) | at-least-once (commit after block write) | at-least-once into Kafka |
| Event-time windows | no | no | **yes, with watermarks** |
| Late-event handling | none — ClickHouse sorts it out later | none | explicit and tunable |
| Joins / session state | no | no | yes, with state |
| Transform on the way in | arbitrary Python | SQL in the materialized view | full streaming SQL |

**Take the Kafka engine** when the job is "move rows from Kafka to ClickHouse"
and no transformation is needed — it is the fewest moving parts, and there is
no process to deploy, monitor, or restart. `./deploy.sh kafka-ingest`.

**Take the Python consumer** when ingest needs logic that does not belong in
SQL — enrichment from another service, custom dead-lettering, bespoke
validation — or when you want ingest observable and debuggable in a language
your team already operates. `./deploy.sh consume`.

**Take Flink** for what only Flink can do: event-time windows with late-arrival
guarantees, cross-stream joins, and per-conversation session state. Here that
is the 1-minute operational rollup. `./deploy.sh submit`.

Run **one** raw-ingest path, never two: two consumer groups on one topic means
every event is inserted twice, and `ReplacingMergeTree` will not save you
because the duplicates have distinct `event_id`s only if the producer says so.

The three things that actually matter in any ClickHouse ingest loop are the
same in all of them, and are the substance of the consumer's design:

- **Batch size** — every `INSERT` creates a part, and every part must be merged.
  One row per insert will hit `too many parts` long before any CPU limit.
  Batches default to 50,000 rows.
- **Flush deadline** — batching alone makes freshness unbounded on a quiet
  topic. Batch size bounds merge pressure; the 2 s timer bounds staleness. Those
  are the two halves of the ingest SLO.
- **Offset commit ordering** — offsets are committed *after* the insert succeeds.
  That makes delivery at-least-once: a crash between insert and commit replays
  and duplicates. The alternative is at-most-once, which silently loses events —
  far worse for billing-adjacent analytics. Duplicates are collapsed by
  `ReplacingMergeTree`.

## Operating it

### SLOs

| Signal | Objective | Where it comes from |
| --- | --- | --- |
| Dashboard API p95 | < 100 ms | `/metrics`, per endpoint |
| Ingest lag (event → queryable) | < 30 s p99 | `max(ingest_ts) - max(event_ts)` in ClickHouse |
| Kafka consumer lag | < 60 s of traffic | consumer group lag |
| Late events dropped | ~0 | Flink `numLateRecordsDropped` |
| Aggregate correctness | views == raw | scheduled reconciliation query |

### Runbook

**API p95 regressed.** Check whether the endpoint reads a view or raw events —
`source` is in every response body. If a view, check `system.parts` for part
count on the target: an unmerged aggregate table is the usual cause. If raw,
confirm the query still prunes with `EXPLAIN indexes = 1`; a query that stopped
matching the sorting-key prefix is the other usual cause.

**Consumer lag climbing.** Lag is the symptom; the cause is almost always the
sink. Check ClickHouse `system.merges` and part counts first — if merges are
behind, inserts slow down and lag follows. Increase batch size before increasing
parallelism; more writers against a struggling table makes it worse.

**`TOO_MANY_PARTS`.** Ingest is inserting too often. Raise
`sink.buffer-flush.max-rows` / `--batch-size`, reduce sink parallelism, and
verify the partition key is not too fine — see stage 3.

**Dashboard disagrees with raw data.** Almost always a view that missed data: it
was created after the rows landed, or the source was mutated. Rebuild the
affected partitions from raw with the backfill in `bench_clickhouse.py`.

**Retention.** `DROP PARTITION` on `conversation_events` is instant and cheap;
never use `DELETE` for retention. TTL handles it automatically.

### Multi-tenant and customer-managed deployments

The whole stack is a set of binaries with no managed-service dependency, which
is what makes a customer-managed or air-gapped installation possible. Tenant
isolation is in the sorting key, so a single cluster serves all tenants with
per-tenant pruning; a customer requiring physical isolation gets their own
instance of the same compose file, with no schema change.

For the two-shard cluster in [`../clickhouse_deployment`](../clickhouse_deployment):
local tables become `ReplicatedReplacingMergeTree`, each materialized view is
attached to the **local** table on every node (never the `Distributed` table, or
rows aggregate twice), and reads go through `Distributed` tables over the
aggregate targets.

## Tests

```
70 passed
```

Every test runs against a **real ClickHouse engine** embedded in-process via
`chdb` — same engine, same SQL, no server and no mocks. A passing test is
evidence the SQL is correct, not that a stub was called.

- **Schema-variant equality** — all four queries, across all six typed schemas,
  must return exactly what the naive schema returns. This is what makes the
  tuning numbers trustworthy.
- **Index pruning is asserted, not assumed** — the bloom filter must measurably
  reduce `rows_read` versus the otherwise-identical unindexed table; likewise
  the sorting key and partition pruning.
- **Materialized-view correctness** — each view must equal a direct aggregation
  over raw events; views must fire on new inserts; merged t-digest p95 must stay
  within 5% of `quantileExact`.
- **`ReplacingMergeTree` dedup** — a replayed batch, the thing at-least-once
  delivery actually produces, must collapse to the original row count.
- **API behaviour** — response shapes, ordering, that resolution and escalation
  rates sum to 1, percentile ordering, bounded windows, rejected injection
  attempts, `/metrics`.
- **Flink SQL and tuning** — watermark declared and configurable, sink batching
  bounded, partition discovery enabled, and the settings that address
  backpressure and hot keys actually switched on.

## Limitations and what I would do next

**Measured on a laptop.** ClickHouse 26.5 embedded via `chdb` on an M3, 12 M
rows. Absolute latencies on server hardware with more cores and real page cache
will differ; the ratios and `rows_read` figures transfer, and `--backend http`
runs the identical benchmark against a real cluster. 12 M rows was the ceiling
that fit in available disk alongside seven copies of the dataset — an earlier
20 M-row run showed the same ordering and larger absolute gaps.

**What has been run end to end, and what has not.** The Kafka → Python consumer
→ ClickHouse → API path is verified on the real docker-compose stack:
320,004 events produced (peak 20.5k events/s), ingested, and reconciled exactly
against the materialized views (`sum(events)` in `platform_daily` == `count()`
in `conversation_events`), with every API endpoint exercised against
ClickHouse 24.8.

The **PyFlink job runs on the cluster** and its output is verified end to end
(1,321 windows emitted and ingested, all minute-aligned, counters internally
consistent — see the Flink section).

What is still **not** demonstrated is Flink under *load*: the backpressure
section describes how to diagnose backpressure rather than a regression driven
to ground here, and there are no numbers for throughput per parallelism level
or for a hot-key fix measured before and after. That needs a sustained load
test at a scale this laptop cannot generate while also running the cluster.

**Exactly-once ends at the sink.** Flink checkpoints exactly-once state, but the
JDBC sink is at-least-once and duplicates are resolved by `ReplacingMergeTree`
on merge, so a query run before merges catch up can double-count. `FINAL` or an
explicit `GROUP BY` closes that window at a cost.

Next, in order of value:

1. **Load-test the Flink job** and publish throughput per parallelism level,
   including a deliberately induced hot-key skew and the two-phase fix measured.
2. **OpenTelemetry traces** end to end — producer → Kafka → Flink → ClickHouse →
   API — so ingest lag is attributable to a stage rather than inferred.
3. **Terraform modules** for the ClickHouse and Kafka topology, so the same
   deployment is reproducible in a customer VPC rather than only in compose.
4. **A tiered-storage TTL** moving partitions older than 30 days to object
   storage, and measure the query latency cost of reading from it.
5. **Schema registry on the Kafka path** (this repo already has Debezium and
   Flink CDC pieces to connect it to) so an added event field cannot break the
   consumer.
